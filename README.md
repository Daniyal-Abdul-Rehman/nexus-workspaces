## Overview

Nexus Workspaces is a B2B collaboration platform where:
- A single authenticated user may participate in multiple organisations
- Each organisation contains projects, tasks, comments, and private project files
- Access is controlled at both organisation and project level
- Security is enforced at the database level, not reliant on frontend logic

The implementation demonstrates:
- Multi-tenant PostgreSQL schema with proper constraints
- Comprehensive Row Level Security (RLS) policies
- Secure invitation workflow with cryptographic tokens
- Optimistic concurrency control for task updates
- Edge Functions with proper security boundaries
- Private Storage with project-level authorization
- Realtime architecture with secure channel authorization
- Performance optimization with strategic indexing
- Automated testing for adversarial scenarios

- Node.js 18+ and npm

## Local Setup

1. **Clone the repository** (if this were a real repo):
   ```bash
   git clone <repository-url>
   cd nexus-workspaces
   ```

2. **Install dependencies**:
   ```bash
   npm install
   ```

3. **Start local Supabase stack**:
   ```bash
   npx supabase start
   ```
   This will:
   - Start local PostgreSQL database
   - Start local Supabase services (Auth, Storage, Realtime)
   - Apply all migrations
   - Generate local environment variables

4. **Link to local Supabase** (if not done automatically):
   ```bash
   npx supabase link
   ```

## Environment Variables

The following environment variables are used:

```bash
# Supabase (auto-generated by supabase start)
SUPABASE_URL=your-local-supabase-url
SUPABASE_ANON_KEY=your-local-anon-key
SUPABASE_SERVICE_ROLE_KEY=your-local-service-role-key

# Edge Functions
WEBHOOK_SECRET=your-webhook-secret-for-signature-verification

# Database (optional, for direct connections)
DATABASE_URL=postgresql://postgres:postgres@localhost:54322/postgres
```

**Note**: For local development, `supabase start` automatically generates the Supabase credentials. The `WEBHOOK_SECRET` should be set in `.env` for Edge Function testing.

## Edge Functions

### invite-member

Creates secure organisation invitations with cryptographic tokens.

**Development invocation:**
```bash
npx supabase functions serve
curl -X POST http://localhost:54321/functions/v1/invite-member \
  -H "Authorization: Bearer YOUR_JWT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "organisation_id": "organisation-uuid",
    "email": "user@example.com",
    "role": "member"
  }'
```

**Production notes:**
- In production, integrate with email service (SendGrid, AWS SES, etc.)
- Remove `invite_url` from response and send email instead
- Ensure proper rate limiting and abuse prevention

### external-webhook

Handles third-party webhooks with signature verification and idempotency.

**Development invocation:**
```bash
curl -X POST http://localhost:54321/functions/v1/external-webhook \
  -H "Content-Type: application/json" \
  -H "x-webhook-signature: sha256=generated_signature" \
  -H "x-webhook-timestamp: current_timestamp" \
  -H "x-webhook-id: unique_event_id" \
  -H "x-webhook-source: stripe" \
  -d '{"type": "payment.completed", "data": {}}'
```

**Production notes:**
- Set `WEBHOOK_SECRET` environment variable
- Implement proper signature verification for your webhook provider
- Configure appropriate time window for timestamp validation

## Incomplete Items

The following items are acknowledged as incomplete or requiring additional work:

1. **Realtime Implementation**: The Realtime authorization function is implemented, but actual Realtime channel subscription testing requires the local Supabase Realtime service to be running and configured. The authorization logic is complete and uses the same `has_project_access()` function as RLS policies.

2. **Email Integration**: The `invite-member` Edge Function returns a development URL instead of sending emails. Production would require integration with an email service provider (SendGrid, AWS SES, etc.).

3. **Performance Testing**: While indexes are designed for scale and seed data includes performance test datasets, actual EXPLAIN ANALYZE output with representative data requires running the local stack with the seed data and executing the hot queries. The framework is in place for performance validation.

4. **Task Revision History**: The ARCHITECTURE.md describes how to implement immutable task revision history, but this is not implemented as it was designated as a design extension rather than a requirement.

## Intentional Deviations from Brief

1. **Token Storage**: The implementation stores SHA-256 digests of invitation tokens rather than using a separate key management system. This is a secure approach that balances security with simplicity.

2. **User Creation**: The seed data creates profile records but assumes corresponding auth.users records exist. In a real scenario, these would be created through the auth signup process.

3. **UUID Strategy**: Some seed data uses hardcoded UUIDs for reproducibility. In production, these would be dynamically generated.

4. **Test Data Volume**: The seed data generates 100K tasks and 500K comments for performance testing, which may be excessive for some local development environments but is appropriate for the performance requirements.

## Deployment to Production

To deploy this to a production Supabase project:

1. **Create a Supabase project** at https://supabase.com
2. **Link to production**:
   ```bash
   npx supabase link --project-ref your-project-ref
   ```
3. **Push migrations to production**:
   ```bash
   npx supabase db push
   ```
4. **Deploy Edge Functions**:
   ```bash
   npx supabase functions deploy invite-member
   npx supabase functions deploy external-webhook
   ```
5. **Set production environment variables** in the Supabase dashboard
6. **Configure Storage buckets** (if not done by migrations)
7. **Enable Realtime** on required tables in the dashboard
8. **Run production tests** with a subset of data
